# DNS records for emersa.io

State on 2026-10-07 (authoritative lookups, plan Appendix A.3): the .io registry delegates `emersa.io` to
`faye.ns.cloudflare.com` and `quinton.ns.cloudflare.com`, the same pair as krupiq.com, so the zone is already in
the Emersa Cloudflare account. The zone has `MX 1 smtp.google.com` (Google Workspace mail works) and nothing
else that matters: no SPF, no DMARC, no `www`, no apex address. A stale DigitalOcean zone (`ns1-3.digitalocean.com`,
`www` pointing at the dead 2023 app) still exists but is no longer delegated; some resolvers may cache it for up
to 48 hours.

Rules that must hold whatever else changes:

- **Never enable Email Routing on the apex.** It replaces the MX records and breaks Google Workspace mail.
  Outbound site mail goes through Postmark for that reason.
- **Do not create an apex `A` or `AAAA` by hand.** Adding `emersa.io` as the Worker's custom domain creates it.
- Keep `MX 1 smtp.google.com` exactly as it is.

## Records to add

| Name | Type | Content | Proxy | Why |
| --- | --- | --- | --- | --- |
| `emersa.io` | TXT | `v=spf1 include:_spf.google.com ~all` | n/a | SPF for Google Workspace. Postmark sends from its own return path (`pm-bounces`), so it needs no SPF include here. |
| `_dmarc.emersa.io` | TXT | `v=DMARC1; p=none; rua=mailto:4d@emersa.io; fo=1` | n/a | Monitoring first. Move to `p=quarantine`, then `p=reject`, once the reports show only Google and Postmark sending. |
| `google._domainkey.emersa.io` | TXT | from Google Admin: Apps, Google Workspace, Gmail, Authenticate email (2048-bit) | n/a | Only if absent; check the Admin console first. Then turn authentication on there. |
| `<selector>._domainkey.emersa.io` | TXT | the DKIM record Postmark shows under Sender Signatures, Domains, emersa.io | n/a | Postmark DKIM. The selector is generated by Postmark. |
| `pm-bounces.emersa.io` | CNAME | `pm.mtasv.net` | DNS only | Postmark custom return path, which gives SPF alignment for DMARC. |
| `www.emersa.io` | AAAA | `100::` | Proxied | A placeholder address so the proxy answers and the redirect rule below can run. |

Then the redirect, under Rules, Redirect Rules (Single Redirects), one rule:

- Name: `www to apex`
- When: Hostname equals `www.emersa.io` (expression `(http.host eq "www.emersa.io")`)
- Then: Dynamic redirect, expression `concat("https://emersa.io", http.request.uri.path)`, status 301,
  "Preserve query string" ticked.

Check: `curl -sI "https://www.emersa.io/docs?x=1"` answers `301` with `location: https://emersa.io/docs?x=1`.

## Optional hardening

- CAA. Cloudflare's universal certificates may be issued by Let's Encrypt, Google Trust Services, SSL.com or
  Sectigo; a CAA set must allow every one Cloudflare uses or renewals fail. If CAA is wanted, add
  `0 issue "letsencrypt.org"`, `0 issue "pki.goog"`, `0 issue "ssl.com"`, `0 issue "sectigo.com"`,
  `0 issuewild ";"` and `0 iodef "mailto:4d@emersa.io"`, and re-check Cloudflare's current CA list first.
- `_mta-sts` and TLS-RPT only once DMARC is at `p=reject`.

## Cutover order (plan 5, M3)

1. Records above, then wait for the DMARC reports to arrive for a few days (they confirm SPF and DKIM pass).
2. Worker custom domain `emersa.io` (deploy.md); "Always Use HTTPS" on; "Under Attack" off.
3. `www` AAAA and the Single Redirect.
4. Delete the stale DigitalOcean zone so nobody re-delegates to it by accident.
5. HSTS preload submission last, only when every host answers HTTPS.
